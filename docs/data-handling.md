# FinShield AI: data handling

Owner: Roopak Dureja. Scope: the `finshield-dev` stack in `ap-south-1`.
Wording follows the team rule: **DPDP-aligned readiness and controls**. FinShield makes no claim of DPDP, SOC 2 or ISO 27001 compliance or certification.

## 1. All data is synthetic

- Every customer, user, document and event is generated by our own scripts. No real person's data is used anywhere.
- KYC images come from `simulator/seed/make_kyc_docs.py`. Each one carries a diagonal **"SAMPLE - NOT A VALID DOCUMENT"** watermark and a **SAMPLE** badge, a plain header such as "SAMPLE IDENTITY CARD - PAN (synthetic)", and a grey silhouette instead of a photo.
- The images contain no State Emblem of India, no UIDAI or Income Tax Department logos, no holograms and no QR codes.
- Names, dates of birth and father's names come from Faker (`en_IN`). PAN values follow the obviously fake pattern `SAMPL0001A` to `SAMPL0200A`.
- Every KYC object is tagged `sample=true` in S3.

## 2. What is stored where

| Data | Where | What is kept |
|---|---|---|
| KYC images (200, PNG) | S3 `finshield-dev-kyc-docs`, keys `kyc/<customer_id>/KYC-<DOC>-<customer_id>.png` | The images themselves |
| KYC file metadata | DynamoDB `finshield-dev-KycFiles` | `file_id`, `customer_id`, `doc_type`, `s3_key`, `size_kb`, `ai_label`, `unmasked_aadhaar_flag` |
| Customer records | DynamoDB `finshield-dev-Customers` | **Aadhaar last 4 digits only** and a **fake PAN**, plus city, loan and agent fields |
| Raw activity events | S3 `finshield-dev-raw-events` | Events as received |
| Normalised events, alerts, approvals, consent ledger, reports | DynamoDB `finshield-dev-<Table>` | Pseudonymised user names (`name_pseudo`) |
| Evidence chain | DynamoDB `finshield-dev-Evidence` and S3 `finshield-dev-evidence` | Hash-chained, append-only entries and exported bundles |
| CloudTrail logs (real mode) | S3 `finshield-dev-trail-<account-id>` | AWS API calls, including KYC bucket reads |

**Where full Aadhaar numbers exist:** only inside the 10 deliberate test images (customers C-10161 to C-10170). Their numbers start with `0`, which real Aadhaar numbers never do. These are the violation FinShield detects. No full number is written to any table, manifest or log; the manifest and tables hold the last 4 digits only.

## 3. Region

All storage, compute and tables are in **ap-south-1 (Mumbai)**. The stack creates nothing in another region.

**Assumption to check:** if `bedrock_model_id` is set to a cross-region inference profile rather than a model hosted in ap-south-1, Bedrock may process prompts in another region of the same geography. Prompts carry only masked text (see section 7). Ajay and Keshav to confirm which model ID is used.

## 4. Encryption

| Store | At rest | In transit |
|---|---|---|
| All 13 DynamoDB tables | KMS, stack key `DataKey` | TLS (AWS APIs) |
| KYC bucket | KMS, stack key `DataKey`, bucket key on; public access blocked | TLS |
| Evidence bucket | SSE-S3 (AES-256); public access blocked; versioning on | TLS |

The `DataKey` can be used only by principals in our account and only through DynamoDB or S3 in ap-south-1.

## 5. Retention

| Data | Kept for | How |
|---|---|---|
| Evidence exports | **1 year, cannot be deleted** | S3 Object Lock, COMPLIANCE mode, 365 days |
| Raw events | **1 year** | S3 lifecycle rule, expires after 365 days |
| CloudTrail logs | 90 days | S3 lifecycle rule |
| Simulated external uploads | 7 days | S3 lifecycle rule (`finshield-dev-external-sim`) |
| Step Functions logs | 14 days | CloudWatch log group |
| DynamoDB tables | Until the stack is deleted; point-in-time recovery on | PITR |

## 6. Who sees what

Sign-in is through Cognito. Accounts are created by an admin only (no self sign-up). Passwords need 12+ characters with upper case, lower case, numbers and symbols.

Every group can read posture, alerts, timelines, the evidence chain (and verify it), report drafts, user profiles, rules, the compliance map and the privacy view. On top of that:

| Group | Extra actions |
|---|---|
| Analyst | Ask FinShield questions about an alert |
| SecurityHead | Approve or reject a lock, release containment, manage approvals and tickets |
| ComplianceHead | Approve or reject a lock |
| Auditor | None: **read-only** |
| Admin | Run scenarios and accuracy runs, run the tamper demo |

Source: the API table in `docs/playbook.md`.

- KYC images are never public. The web app opens one only through the API, which checks the user's group, records the view and returns a short-lived presigned URL.
- The Evidence table is **append-only**: only `finshield.evidence.append()` writes to it, and no IAM role has `UpdateItem` or `DeleteItem` on it.

## 7. Personal data and AI

- **Code computes every number, score and severity. Bedrock only writes words.**
- Text sent to Bedrock passes a Bedrock Guardrail that anonymises names, emails, phone numbers, 12-digit Aadhaar-style numbers and PAN-style values, on input and output.
- The KYC labelling step reads an uploaded image, records its document type in `ai_label`, and sets `unmasked_aadhaar_flag` when a full 12-digit number is visible.

## 8. Aadhaar vault assumption

UIDAI requires entities that store Aadhaar numbers to keep them only in a separate, encrypted **Aadhaar Data Vault**. FinShield assumes the lender already runs such a vault outside FinShield. FinShield itself stores no Aadhaar number, only the last 4 digits, so it is not a vault and does not need to be one. A full number found in a stored image is treated as a data-handling violation and flagged.
